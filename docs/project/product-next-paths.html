远景（说清楚）

Vibe Control = agent-facing、provider-backed 的控制产品。
主操作者是 coding agent。它不替代 Cursor/Claude/Pi，也不替代 NotebookLM/Beads。 它做的是：把「某类场景」接到「某个 provider」上时，用统一 CLI / 信封 / 闸门，让 agent 可重复、可降级、可变异受控。
是不是
Engine + Capability Profile + 可启用能力（knowledge / task；未来 sdd/tdd…） SSOT 管理产品 / 规格编辑器
场景 → provider 适配层（今天：SSOT 事实查询 → NotebookLM；任务跟踪 → Beads） 又一个 coding agent / workflow 引擎 / durable session 平台
默认关能力；无 provider 则无法 enable 自动替人/agent 打开一切

今天 knowledge 主要服务「从已同步的权威文档回答」——当前场景是 repo 里的 SSOT 语料。 未来可能有别的 knowledge 场景（尚未定）；那也仍是 knowledge 能力 + 某 provider，不是「SSOT 功能」。

正确分层（修订图）

上一版把「Repo SSOT」画进 Vibe 功能框是错的。正确说法： knowledge 能力 当前把「权威文档语料」同步到 NotebookLM 并做受控 ask； 语料往往来自 git SSOT，但 SSOT 管理本身不是产品卖点。

价值：为什么 agent 不直接用 provider？

这是产品买点。直接 notebooklm ask / bd … 当然能用；Vibe 解决的是 agent 规模化踩坑：

直连 provider 时 agent 常怎么翻车Vibe 适配层做什么
乱问、聊天记忆当证据、没有固定答案形状 Ask 政策（persona + template + --new）+ Facts/MUST 契约
notebook 里混着旧源 / 孤儿源，答案被污染 sync inventory、ask hygiene、cleanup-candidates（只读）
不知道该同步哪些文件、乱 add/delete allow_list / 语料选择 / 审批矩阵 / 默认不突变
provider 挂了仍假装「全绿」 repo fallback + 诚实 degraded；product_ready 门禁
每个 repo 自己拼 CLI 参数与登录流程 统一 vibe 信封：code / next_actions / mutation 标志
能力默认全开，agent 乱碰 live Beads Capability Profile 默认关；live 双闸门
一句话买点： Provider 解决「有没有能力」；Vibe 解决「agent 用这能力时别瞎、别越权、失败别装没事」。

明星 / 同类产品：他们到底解决了 agent 的什么问题？

调研结论：真正「火」且对 agent 有用的，多半不是又一个 harness，而是接地 / 省 token / 跨会话任务记忆。

产品对 agent 的硬问题买点（人话）对 Vibe 的启示
NotebookLM（+ Claude 社区用法） 上下文塞爆；答案无出处 源锚定检索 + citation；研究与实现分离 我们已站在这 provider 上；要强化的是语料是否干净、问法是否确定
Beads (bd) compaction 后失忆；不知道下一步 bd ready 机器可读；依赖图；git 内任务记忆 不要重做 Beads；Vibe 做就绪/闸门/（可选）托管投影
CLAUDE.md / AGENTS.md 每轮行为漂移 短规则常驻；知识别塞进行为文件 Vibe skills 保持薄；知识走 knowledge，不塞满 skill
Knowit / AKB / Engram 类 跨会话工程记忆 结构化记忆 + MCP；git 友好 他们是「另一类 knowledge provider 候选」；我们不必现在换，但接口要能换
Pi harness 太重 / 不可定制 极简四工具 + 扩展 借「少默认、按需」；不跟它抢 harness
Eve 生产 agent 易断、难审 durable + sandbox + HITL 借「卡点可见 + 审批清晰」到 doctor/信封；不抄运行时
RRCE 等 MCP 全家桶 知识+任务+RAG 一把梭 一站式 MCP 警惕 范围膨胀；我们偏「薄控制面」而非全家桶
亮眼差异（对我们）： 市场上多数明星要么是 provider 本身（NotebookLM / Beads），要么是 harness（Pi / Eve），要么是 又一个记忆库（Knowit/AKB）。 Vibe 的空位是：把这些 provider 接到 agent 工作流时的控制与适配——同步范围、ask 政策、能力开关、突变闸门、失败诚实。 这不够「炫」，但对「给 agent 用」恰恰是缺口。

Knowledge（能力）— 当前场景与缺口

能力 knowledge   provider NotebookLM   当前场景 权威文档语料上的确定问答（常来自 git SSOT）

Agent 需要「规格到底要求什么」
        │
        ▼
vibe knowledge query   ← 走 Ask 政策，不是裸 notebooklm ask
        │
        ├─ 证据不足 → agent 改 git 文档（真源）→ sync --apply → 再 query
        └─ MUST 清晰 → agent 实现 / 建任务

缺口仍是：写作要利于检索、golden 问法、sync 后 ready。未来其他 knowledge 场景未定，不提前画饼。

Task（能力）— 路径 A 比「create/close」更宽

能力 task   provider Beads   Consumer 日常主要走路径 A

路径 A：agent ↔ Beads（Vibe 负责就绪；查询/编排可以更复杂）

vibe task status / doctor     →  TASK_READY？
        │
        ▼
agent 用 bd（provider 原生）可能做很多事，不只 create/close：
  · bd ready / list / show     ← 查「现在能干什么 / 某任务状态」
  · bd create / update / close
  · bd dep / blocked           ← 依赖与阻塞
  · 多任务并行、发现新任务再挂上
        │
        ▼
Vibe 今天：证明 provider 可用 + 能力开关 +（可选）managed live 闸门
Vibe 以后可能补：统一 status 信封、只读汇总——仍不是重做 Beads

路径 A（优先写清）

  • Consumer = agent
  • 日常：bd 查询 + 变更
  • Vibe：enable / doctor / TASK_READY
  • 复杂查询是预期，不是例外

路径 B（后做 / 写死边界）

  • vibe task apply → live Beads
  • 双闸门，默认关
  • 决策：B-关 或 Option B
  • 不要让 agent 以为这是日常

安装一条线（只负责「把 CLI 装上」）

话术「安装并学习 https://github.com/mike-boost/vibe-control」= 装机，不是每个 consumer 都去 clone 产品 repo。 装完后的「学习」应落到上一节的 describe / --help / skills。 

Agent 收到产品 GitHub URL（装机）
        │
        ▼
[0] clone / 最新 release
[1] ./scripts/install-user.sh → ~/.local/bin/vibe
[2] vibe --version
[3] vibe skills install --apply   （可选但推荐）
[4] vibe describe --json          ← 用 CLI 学控制面，不读源码树
        │
        ▼
之后在任意 consumer repo：
  config → doctor → enable knowledge/task → query 或 bd …
